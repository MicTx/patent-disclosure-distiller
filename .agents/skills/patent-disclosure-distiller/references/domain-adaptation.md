# 跨领域适配与追问协议

## 1. 适配原则

跨领域时分两步：先按 `methodology.md` 0.1 选择技术路线（`DATA_CONTROL_LOOP` / `STRUCTURE_PHYSICS` / `HYBRID`），再按路线迁移关系，不迁移样本名词、参数或效果数字。

`DATA_CONTROL_LOOP` 关系链：

```text
可观察事件/数据
  → 状态或表示
  → 模型/规则路由
  → 预测、评分或候选决策
  → 资源/控制/调度动作
  → 结果验证与错误代价
  → 模型、策略、版本或资源更新
```

`STRUCTURE_PHYSICS` 关系链（机械、材料、结构主题使用，不套上面这条）：

```text
部件/材料 → 连接/界面关系 → 运行或制造步骤
→ 物理约束（受力/温度/尺寸/公差/安全） → 失效模式与防护 → 验证
```

`PROCESS_PROTOCOL` 关系链（实验室流程、检测、化学反应、操作规程主题使用）：

```text
原料/对象 → 步骤与工艺参数 → 中间态
→ 温度/时间/纯度/安全约束 → 偏差与污染处理 → 检测验证
```

所有路线均不匹配且材料不足以判断时，降级为 `INTAKE_DRAFT`，把"属于哪条路线"列为首要追问。

每个领域重新确认：

- 观察对象、数据来源、时间粒度、身份和版本；
- 哪些变量是事实、标签、推断、预测和反馈；
- 资源或动作单位、成本、容量、权限和安全责任；
- 长期依赖、外生变量、模型阶数、规则或成本函数；
- 低信息、低置信度、冲突、失败、回滚和人工确认路径；
- 指标、基线、样本、环境、统计方法和原始记录。

不要因为两个主题都包含“预测”“智能”“用户行为”就默认同一模型、状态粒度或决策规则。

## 2. 输入形态分支

### 2.1 材料完整

先做证据清点和冲突扫描，再按已选路线复原：`DATA_CONTROL_LOOP` 按 `O→S→M→D→A→V→U`；`STRUCTURE_PHYSICS` 按 `methodology.md` 0.1 的结构链。完整不等于可验证：若公式、接口、实验或边界缺失，保留 `[Q]`，不补猜测。

最少输出：标准交底书全字段、证据定位、冲突表、待补信息和自审结果。

### 2.2 只有碎片想法

先把碎片分成“对象、场景、现象、目的、候选机制、输入、输出、约束、已知证据、假设”。无法确认的句子不润色成事实。

先交付两层：

1. **最小可用骨架：** 题名候选、问题、总体链路、候选步骤、实施例占位和明确 `[A]/[Q]`。
2. **高价值追问：** 优先问会改变技术关系的问题，不先追问不影响方案的文案细节。

### 2.3 需要改写现稿

保留原稿事实和定位，建立“原句—问题—改写—证据状态”表。优先修复：术语混用、输入输出跳步、空泛效果、未经证据的强断言、参数作用域冲突和异常路径缺失。不要为了“更像专利”静默改变技术语义；改变语义的地方标 `[I]/[A]/[Q]`。

### 2.4 跨领域

先写“抽象链路”，再把领域名词映射到链路节点。实施例应替换状态、资源、约束和验证口径，而不是把地图/某一行业的参数直接复制过去。

### 2.5 非技术化主题或业务愿景

把“想提升效率/体验/安全/转化”拆成：

- 可观察对象和事件是什么？
- 系统在哪个时点需要作出什么技术选择？
- 输入从何处取得？
- 哪个处理关系改变了系统行为？
- 输出由哪个模块、设备、接口或资源消费？
- 如何处理错误和验证结果？

若材料只能回答商业目标，不能形成可观测输入、处理关系和工程动作，则输出“技术化澄清版/待验证构想”，不强行生成完整专利方案。

## 3. 领域适配卡

以下只是追问和映射示例，不是领域事实或法律意见。

### 3.1 工业物联网/预测性维护

| 主链 | 适配问题 | 需要确认 |
|---|---|---|
| `O/S` | 传感器序列、工况、维护记录如何形成状态？ | 采样率、校准、设备族、漂移、缺失、标签延迟 |
| `M/D` | 异常、寿命或规则模型如何根据停机/误报代价选择？ | 评分校准、阈值、成本函数、模型版本 |
| `A` | 预测如何转为检修优先级、备件预留和停机窗口？ | 安全联锁、库存、人工确认、调度接口 |
| `V/U` | 实际故障、维修和误报/漏报如何反馈？ | 观察窗口、基线、上线审批、回滚 |

不能把“预测风险”直接写成“自动停机”；高影响动作需写权限、联锁、人工确认和回滚。[L/Q]

### 3.2 医疗影像或医疗工作流

仅写影像处理、检查排序、资源调度等技术流程，不把工作流预测升级为诊断或治疗结论。确认数据授权、脱敏、设备协议、患者/检查标签来源、人工复核、接口版本和责任边界。效果使用队列完成时间、失败重扫、资源冲突或传输指标；医疗功效和合规结论另行审查。[L]

### 3.3 防御性网络安全

仅适用于明确授权的监测、测试、事件响应、CTF 或安全研究。将日志、资产、身份、时间关系和告警状态分开；把评分/预测转成工单、采集更多日志、隔离建议或需审批的受控动作；高影响动作须最小权限、审批链和回滚。确认日志完整性、时钟同步、证据保全、误报/漏报分母和数据保留。

不得在交底技能中扩写破坏、DoS、大规模目标操作、供应链入侵、凭据窃取、检测规避或未授权访问流程。若用户要求这类内容，维持技术交底的防御边界并改问授权、目标和安全控制。

### 3.4 云平台/资源调度

将请求序列、租户、区域、负载、缓存命中、版本和成本表示为状态；输出预取对象、并发上限、TTL、回源和取消计划。重点确认多租户隔离、容量、成本预算、过期、区域故障、旧版本响应覆盖、限流、重试和回滚。指标应区分命中率、可用时间、无效字节、回源次数、成本和尾延迟。

### 3.6 机械结构 / 工艺流程（STRUCTURE_PHYSICS / PROCESS_PROTOCOL 示例卡）

| 环节 | 结构路线追问 | 工艺路线追问 |
|---|---|---|
| 对象 | 部件清单、材料、连接方式是否给全？缺哪个部件的对手件？ | 原料/样本、试剂、设备清单是否给全？ |
| 步骤 | 装配/运行顺序、每步的承载与行程？ | 操作顺序、每步的参数（温度/时间/用量）与中间态判据？ |
| 约束 | 受力、公差、磨损、误操作边界？ | 温区、时限、纯度、安全与污染边界？ |
| 失效/偏差 | 何种失效模式、何种防护或止逆特征？ | 何种偏差、如何隔离处置、谁判定？ |
| 验证 | 强度/疲劳/探棒/加载试验条件与判据？ | 对照、重复次数、检测方法与记录字段？ |

结构稿不写预测准确率、缓存或在线更新；工艺稿的异常用"偏差/污染/超时/中断"表述，不套计算层词汇。效果未实测时一律"设计目标/待验证"。

### 3.7 业务流程、运营或非技术产品

不要把“推荐策略/智能运营/增长系统”直接当发明点。追问是否存在软件、数据结构、处理规则、控制时序、资源组织、设备连接或可观测系统效果。若技术动作只是人工流程或商业规则，明确标记其可能属于非技术内容并由专业人员另行判断；本技能不下法域结论。[L]

## 4. 追问优先级协议

### Q1 交付范围

- 这是技术底稿、改写稿、待实验方案还是完整申请准备材料？
- 哪些是已实施事实、实验结果、设计目标、假设或外部观点？
- 是否需要摘要、附图、权利要求支撑映射和实验方案？

**未闭合处理：** 继续可交付底稿，但在首页写清范围；所有效果和法律比较降级。

### Q2 术语和变量关系

- 当前事件、历史事件、用户目的/标签、预测事件是否为不同字段？
- 标签来自日志、人工标注、规则还是模型？生成时点是什么？
- 场景、资源、反馈的唯一键和版本是什么？

**未闭合处理：** 冻结依赖字段的模型、效果和候选支撑，输出字段对照表。

### Q3 输入—处理—输出

- 每一步输入来自哪个接口、日志、设备或人工确认？
- 处理规则、公式、模型版本和参数在哪里？
- 输出由哪个模块或资源消费者使用？
- 缺失、重复、延迟、冲突和未知如何处理？

**未闭合处理：** 该步骤写成 `[Q]`，不使用“智能确定/动态调整”填空。

### Q4 公式、参数和边界

- 参数是固定、配置、实验还是反馈值？范围、单位、版本和作用域是什么？
- 如何归一化、平滑、处理零频率、并列、低置信度、溢出和边界？
- 模型/策略更新的触发、幅度、发布和回滚是什么？

**未闭合处理：** 数字仅作示例或待定参数；要求提供公式、伪代码和样例输入输出。

### Q5 验证与效果

- 指标分子、分母、基线、样本、时间窗、设备、网络、负载和统计方法是什么？
- 原始日志、脚本、配置和结果在哪里？
- 是单次、平均、分位数还是区间估计？

**未闭合处理：** 改写为“设计目标/机制预期/文档声称/待验证”。

### Q6 替代方案和边界

- 换数据源、模型、设备、协议、缓存或调度策略后，哪些关系保持？
- 哪些参数是必要条件，哪些只是一个例子？
- 高影响动作是否需要人工确认、权限、审计或回滚？

**未闭合处理：** 将替代方式列为 `[A]/[Q]`，不把产品场景列表当作泛化证据。

## 5. 追问输出格式

```markdown
### 待确认问题 Q-001
- 问题：[一句话可直接回答的问题]
- 当前状态：[材料事实/冲突/缺失]
- 影响：[字段、步骤、效果或支撑映射]
- 最小关闭证据：[日志字段/公式/样例/实验/负责人确认]
- 未关闭前写法：[允许使用的降级句]
```

## 6. 非技术化主题的转化示例

**原始想法：**“让仓库更智能，减少找货时间。”

**不应直接写：**“通过 AI 优化仓库效率，显著减少时间。”

**应追问/转化：**

- 观察：扫描枪、订单、货位、库存和人员位置有哪些可取得事件？
- 表示：怎样形成订单状态、货位状态和路径/任务状态？
- 决策：系统在拣货任务开始前选择什么？候选货位、路线、批次还是调度顺序？
- 动作：哪个终端或调度器执行，是否涉及锁定、并发和权限？
- 错误：库存不一致、货位占用、网络中断、任务取消如何处理？
- 验证：找货时间的起止点、基线、订单分层和原始记录是什么？

在得到这些信息前，可输出 `[A]` 的候选链路和 `[Q]` 台账，但不补算法、时间数字或效果结论。

## 7. 跨领域自审

- 是否重新定义了目标领域的状态、资源和约束？
- 是否误把领域名词、数字、网络条件或效果复制为通用规则？
- 模型输出是否真正落到工程动作，而非停在“预测/评分”？
- 是否有低信息、低置信度、错误代价、人工确认、权限和回滚路径？
- 效果是否重新设计指标和基线，而不是沿用样本数字？
- 涉及医疗、网络安全、隐私、工业安全或高影响决策时，是否把技术描述和合规/法律审查分开？
